## How JARVIS is wired

- **Entry point:** `src/main/main.js` (Electron main). It builds one `ctx` object and wires every part to it. `package.json` has two scripts: `start` (`electron .`) and `test` (`node --test`).
- **Turn flow:** `src/core/orchestrator.js`. User text → `fastPath` (confirm, memory and media skills, no model) → `brain/router.js` picks quick chat or tools → `skills/select.js` picks the skill groups → the provider (`providers/ollama.js`) streams → tools run through `tools/registry.js`.
- **Skills and tools:** a skill group is `src/core/skills/<id>/index.js` exporting `createGroup(deps)`. The order is the `ORDER` list in `src/core/skills/index.js`. Tool bodies are in `src/core/tools/*.js`. `brain.defaultCatalog(deps)` builds the catalog (16 groups and 89 tools with the new group).
- **Configuration:** `src/core/config.js` (`DEFAULTS`, and `merge()` validates every key) reads `<data>/config.json`. `src/core/settings.js` validates patches from the settings window. Data is in `%APPDATA%\jarvis-core`.
- **Other parts:** voice (`src/core/voice`), wallpaper bridge (`bridge.js`), Chrome extension link (`media/ytmusic-link.js`), PowerShell hosts for PC control, media and speech, timers, proactive speech.

## Findings

### Fixed

1. **Medium: one broken skill group stopped the whole app.** `loadGroups` called `require` and `createGroup` with no guard, so a throw in any group file ended `main.js` at load. It now loads the rest and records the failure in `catalog.missing` ([src/core/skills/index.js:9](../src/core/skills/index.js)); `main.js` logs it and the new tools report it.
2. **Medium: questions about JARVIS itself got no tools.** "run diagnostics" or "what can you do" matched nothing in the router and went to quick chat, where the model answers from the prompt alone. The new `SELF` pattern routes them to tools ([src/core/brain/router.js:10](../src/core/brain/router.js)). These questions now take a full model turn instead of the quick one.
3. **Low: `applyPatch` wrote into the config it was given.** `user` was not copied, so a name change mutated the live config before it was saved, and was dropped silently on a frozen object ([src/core/settings.js:8](../src/core/settings.js)).
4. **Low: the log lost what it needed for an error view.** Bus warnings were written without their level, and failed tools, failed turns and unhandled promise rejections were not written at all. All four are now logged ([src/main/main.js:304](../src/main/main.js) and the lines above it).
5. **Low: small drift.** The sysmon address was written out twice in `main.js` next to the `SYSMON` constant; a comment about proactive speech sat above `pc` in `config.js`; the prompt test built its own older dependency list and skipped the newer groups ([test/prompt-tools.test.js](../test/prompt-tools.test.js)).

### Open, for your review

1. **Medium: the prompt states the default hotkeys as fact.** [src/core/brain/prompt.js:91](../src/core/brain/prompt.js) and the quick-chat prompt say "chat on Ctrl+Space, voice on Ctrl+Shift+Space", but both are settings (`config.hotkeys`). After a change in settings JARVIS tells the user the wrong keys.
2. **Medium: a prompt rule contradicts two tools.** [src/core/brain/prompt.js:64](../src/core/brain/prompt.js) says "You have no control of lights, appliances, brightness, displays", while the audio-display group has `brightness_set` and `displays_list`. The rule adds "beyond your listed tools", but a small model may still refuse.
3. **Medium: no handler for uncaught exceptions in the main process.** I added logging for unhandled rejections only. A handler for `uncaughtException` changes how Electron reports a crash, so I left that choice to you.
4. **Low: three hand-kept lists repeat what the tools already say.** `TOOL_HINTS` (one entry per tool), the confirm list at [src/core/brain/prompt.js:112](../src/core/brain/prompt.js) (same as `risk: 'confirm'`), and `UNTRUSTED_TOOLS` in [src/core/brain/guard.js:30](../src/core/brain/guard.js) (a subset of the `untrusted` flags). They agree today; only the first is guarded by a test.
5. **Low: `risk` is unset on 31 tools and `'safe'` on the rest.** Both mean the same to the runner.
6. **Low: files that grow without limit.** `voice-trace.jsonl` ([src/main/main.js:272](../src/main/main.js)), `actions.log` and `music-plays.jsonl` are appended forever. Only `jarvis.log` rotates (512 KB).
7. **Low: the offline library folder is fixed in code** as `C:\JarvisData\library` ([src/main/main.js:129](../src/main/main.js)), not a setting.
8. **Low: dead or repeated code.** `jarvis_status` has a label for `uptime` that nothing supplies ([src/core/tools/skills.js:120](../src/core/tools/skills.js)); the mic on/off rule is written twice ([src/main/main.js:307](../src/main/main.js) and :309).

## The new tools

A new skill group, `self` ([src/core/skills/self/index.js](../src/core/skills/self/index.js)), loads when the user asks about JARVIS itself, or through `more_skills`. It is not in the always-loaded core group, so ordinary turns do not pay for it.

| Tool | Say | Reports |
|---|---|---|
| `self_diagnostics` | "run diagnostics", "is everything working" | 23 live checks, problems first: model, speech-to-text, text-to-speech, wake word, microphone, voice recognition, wallpaper link, Chrome extension, browser skills, sysmon, offline library, online lookups, PC control, media, timers, hotkeys, settings file, data folder, startup result, skill groups, tool failures since start, faults in the log |
| `skills_list` | "list your skills", "what can you do" | Every group and tool from the live catalog, whether a group can work now, groups that failed to load, tools that failed since start. With `group`: each tool of that group with a one-line description, "asks first" marks and call counts |
| `self_config` | "what version are you", "show your settings" | Version, Electron and Node versions, uptime, data folder, every setting changed from the default, entries in `config.json` that are ignored |
| `self_log` | "show recent errors", "what went wrong" | The latest fault lines of `jarvis.log`, or all lines, with an optional text filter. Marked untrusted, like other text from outside |

Each check has three results: ok, off (switched off or not installed, not a fault) and problem.

Where the data comes from:

- **Skills:** the catalog the tool runner dispatches from, handed to tools as `ctx.skills` ([src/core/tools/registry.js](../src/core/tools/registry.js)). The runner also counts calls and failures per tool.
- **Whether a group can work:** an optional `status()` on the group. Browser, system and knowledge have one; the others report as loaded.
- **Settings:** `inspectConfig()` in [src/core/config.js:141](../src/core/config.js), which runs the same `merge()` the app uses.
- **Checks:** [src/main/checks.js](../src/main/checks.js) reads the live `ctx` on every run.
- **Faults in the log:** a word match on free text (`error`, `failed`, `warn`, `OFF` and similar), not a log level. It can miss a fault or count a harmless line.

Tests: [test/self-tools.test.js](../test/self-tools.test.js) and [test/self-checks.test.js](../test/self-checks.test.js). To run the tools against the real app, set `JARVIS_SELFTEST_MODE=self`, `JARVIS_SELFTEST=<out folder>` and `JARVIS_DATA_DIR=<temp folder>`, then `npm start`; the output is in `report.json`.
